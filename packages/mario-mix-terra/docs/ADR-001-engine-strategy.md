# ADR-001 · 第三期泰拉瑞亚：先模块化，暂不整包更换游戏引擎

记录日期：2026-09-16  
状态：本轮建议执行路线，可在测量和原型验证后复审。  
范围：以用户本次上传的 `mario-mix-3.zip` 为唯一迁移底稿。前两期的独立发布文件、网站和未完成的城堡关均不修改。

## 1. 结论

这轮需要结构性重构，而不是继续添加补丁；但暂不把整份游戏移植到 Phaser、Godot 或 Unity。

保留现有游戏规则、物理时序、角色与关卡行为，建立清晰的运行时、玩法、渲染、输入、音频、UI 和内容边界。通用库并非禁用：出现明确需求时可以采用成熟实现；不要为了保持“零依赖”长期自制所有基础设施。

先把引擎相关依赖留在边缘接口，再决定是否更换某一部分。这样可以先得到可协作版本，也降低以后接入成熟引擎的代价。

## 3. 为什么先不整包迁移

1. 当前观察到的首要问题是共享状态、补丁覆盖链、资源与代码混放、UI/输入生命周期交叉。仅换框架不能自动消除这些关系。
2. 平台下穿、挖掘/放置、坐骑与地形互动、伤害无敌帧、Boss 阶段、隐藏关返回等，都需要明确规格与原行为对照。使用新框架的默认碰撞并不能保证这些行为相同。
3. 浏览器试玩与可下载版本仍是当前交付方式。完整引擎迁移会引入新的构建和部署验证项，必须由实际收益支撑。
4. 不采用“大重写”也不等于永远维持原架构。只拆文件、仍依赖同一个巨大闭包和执行顺序，不计为完成模块化。

## 4. 目标边界

```text
app/          启动、暂停、返回菜单、场景切换
runtime/      固定时钟、场景生命周期、资源与平台接口
input/        键鼠/手柄/触屏 -> 语义动作
simulation/   角色、碰撞、武器、敌人、Boss、掉落和建造规则
content/      地图、物品、角色、敌人和资源清单
render/       读取状态并绘制；不推进掉落、伤害或计时
ui/           HUD、菜单、背包、设置和帮助
compat/       尚未迁出的底稿依赖；明确标注，不扩大
build/        生成浏览器版本和可下载版本
```

这是职责规划，不是说目录已全部实现。

约束：
- 游戏规则不能依赖具体 DOM 节点或某个 Phaser/Pixi 类型。
- 输入读取只有一个明确所有者；菜单焦点与游戏输入通过路由规则分流。
- 游戏更新有一个可追踪的主入口；物理、伤害、掉落、计时各有明确执行次序。
- 绘制不能同时偷偷修改玩法状态。
- UI 通过命令请求行为，通过只读状态显示结果；不直接操作任意全局变量。
- 状态与资源按关卡生命周期清理，场景退出负责释放监听器与音频。
- 优先使用简单模块与明确接口；不先建设通用 ECS、万能插件市场或大而全的自研引擎。

Godot 的官方场景组织建议强调独立职责、低耦合、显式提供依赖；Phaser 官方场景系统也将加载、主菜单、关卡与叠加 UI 作为可独立管理的场景。采用这些组织原则不要求先迁移到对应引擎。[1][2]

## 5. 候选技术与复审条件

| 方案 | 本轮判断 | 什么时候重新考虑 |
|---|---|---|
| 现有 Canvas/Web Audio + 模块化 | 主线方案 | 性能或重复基础设施开发成本有明确证据后复审 |
| PixiJS 渲染层 | 备选；不是完整游戏引擎 | 绘制、图层、粒子或效果是已测量瓶颈，原型优于现有实现 |
| Phaser 框架 | 备选整合方向 | 新章节需要大量场景、动画、资源、镜头基础设施；小切片验证能保留现有行为 |
| Godot | 当前不整包迁移 | 产品目标转为编辑器驱动、原生桌面/移动端优先，并接受部署方式变化 |

Phaser 内置 Arcade 和 Matter 两套物理，但是否启用需要配置，不能把采用 Phaser 与强制替换现有物理混为一谈。[3] PixiJS 核心是渲染，分层与图形管理是其能力范围，不会自动处理全部游戏规则。[4][5] Godot Web 导出可用于浏览器，但涉及 WebAssembly/WebGL 2.0 与特定导出条件；不能把“支持 Web”当作与现有下载包完全等价。[6]

不同时引入多套库来负责同一件事。是否迁移，比较相同素材、分辨率、实体数量、输入回放下的帧时间、内存、首屏资源、交互和维护成本。基线测量完成之前，不承诺替换后更快或更轻。

## 6. UI 处理

UI 统一不是更换引擎的充分理由。先分离 HUD、菜单/设置、帮助三层，统一间距、色彩、字号、输入提示和焦点状态。与世界同步的准星、血条等可留在绘制层；菜单与改键可以采用浏览器界面。

不得用个人网站的版式直接挤占游戏画面。结构等价迁移和视觉修改分开提交，避免看起来变漂亮的同时改变判定或操作。

## 7. 交付步骤与验收门槛

### A. 可重建基线
保存原始校验值，盘点内嵌/远程/缓存资源，分离可维护源码与生成产物。开发源码可拆开，下载版本可由构建生成；离线范围依资源实际可用性标注，不把外链内容说成完整离线。

### B. 第一批真实模块
先输入与资源边界，再场景生命周期和 UI，随后逐项整理武器/物品、敌人/Boss、地形互动。迁移时临时适配层可以存在，但每个模块要说明已解耦还是仅搬运。

### C. 原行为对照
使用同一初始状态和输入序列，对比位置、速度、装备/物品数量、伤害、场景切换。先控制随机源、资源就绪状态和时间，不把非确定性的正常差异误认成成功或失败。补充人工通关、真实手柄、音频与浏览器加载验收。

### D. 引擎复审
先在一个独立场景或渲染试验中证明收益，再决定是否扩大迁移。不得让原型版本覆盖稳定版。
