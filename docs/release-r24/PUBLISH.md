# 发布目录与部署方式

## 开发资料和网站文件分别管理

|内容|保留位置|进入网站发布目录|
|---|---|---|
|已发布游戏、作品介绍、主站资源|原网站目录|是，保持原版本|
|当前源码下载、W02 模板下载、公开贡献指南|明确的公开入口|是|
|当前版本、角色、关卡现状与公开任务|从真实数据生成|是，清理交接字段后生成|
|测试脚本、夹具、安装器、备份、交接记录|源码工作区和有意提供的源码 ZIP|不作为松散网站路径发布|
|当前游戏候选生成目录、未发布城堡代码|开发工程|不自动替换稳定试玩|

源码 ZIP 是明确提供给贡献者的工程下载，包含测试与文档是有意设计。源仓库仍然可公开访问；这里不是权限系统或保密措施。旧有效下载、权利声明和署名不删除。动态使用的背景、角色和资源保守保留，不能因为没有静态引用就自动删除。

## 生成与检查

`release:prepare` 读取原工作区，调用现有生成器，在内存中生成公开内容并扫描引用，然后才写 `.local/publish`。不会覆写作者任务、原游戏或原文档。主要检查：

- 入口、图片、CSS、JS 模块和登记资源引用的存在、路径大小写和危险路径；重复标识、标题层级的基本结构、链接名称及替代文字。
- 当前源码版本/下载哈希/归档成员与工作区源码一致；W02 下载及其固定 M06 运行时一致。
- 下载 ZIP 实際解压数据与 CRC；非法路径、重复成员、过大扩展、异常文件类型。图片进行基本文件标识与 LFS 指针检查，不冒充所有图片的完整像素解码。
- 公开页面和任务数据中已列出的内部措辞、占位域名与本地网址；工程管理路径和测试入口不得成为公开链接。
- 静态页面、数据脚本和懒加载模块使用同一份产物的缓存版本；生成站点版本和 sitemap。

任意阻断项都不会产生新的发布目录。旧目录手工修改、有未知新文件，或检查后源码发生变化，都会停止替换。相同输入的再次生成没有写入。

`release:check` 重新计算源文件与产物身份，检查整个发布目录，不只检查一个版本字符串。外部链接、运行时按条件构造的远程资源、所有真实设备仍需人工和浏览器验收；审计输出保留需要检查的外部 URL。

## 方式一：只上传已验收的发布目录

完整验收后，将 `.local/publish/` 中的内容上传至独立静态站点或专门发布分支。网站路径从这个目录作为根开始。不能上传上层 `.local`，也不能用本更新包 payload 替代网站。

GitHub Pages 若仍从主分支根目录部署，工作区的测试与工程页面仍可能被发布。`.nojekyll` 不负责过滤这些文件。应将发布源切换为 GitHub Actions，或使用只包含核验产物的单独分支。此设置需维护者手动操作，本包未执行。

## 方式二：可选的手动 Actions 流程

`pages-workflow.example.yml` 放在文档目录，**不是已启用的工作流**。先审阅，再复制到 `.github/workflows/publish-approved.yml`，并在仓库 Settings → Pages 中选择 GitHub Actions。示例只有手动 workflow_dispatch，不新增自动定时发布。

在相同源码下本地完成生成、预览和实机验收，填写 `.local/release-r24/acceptance.json`。需要 CI 复核时，将确切记录复制为 `.github/publication-approval.json`，核对其中不含私人路径或信息后提交。该批准文件不属于网站公开产物。流水线重新生成，只有源指纹与产物指纹均一致才上传；工作树与 CI 不一致时应核对、重建并重新验收，不应手工伪造哈希。

示例使用官方 Actions 的主版本标签；维护者可按自己的供应链策略固定为已审核的提交。远端 Actions、Pages 权限和这个示例本轮未实际执行。已有工作流是否同时上传仓库根目录，也需要在真正仓库中审查并停用或更改，避免两套部署互相覆盖。
