# 页面与内容规范

## 先回答访客的问题

栏目首页回答“这里有什么项目、最近有什么变化、怎样参与”。项目概览回答“它是什么、现在能体验什么、当前重点是什么”。不把路径、提交哈希、安装器输出、维护者表单作为主内容。

现有六项导航保持：首页 / 项目 / 游戏 / 工具 / 开发日志 / 关于。“项目”是作品展示，“开发日志”是制作过程；二者可交叉链接，但不重复整页作品介绍。

## 层级

`/notes/` 是跨项目目录，不是某个游戏的任务板。项目路径使用稳定 ID：`/notes/<id>/`。概览、任务、资料、更新、参与是项目内导航；交接仅在页尾作为维护入口。资料详情有返回项目资料的面包屑。历史 `/dev/` 进入相应项目，不新增一个平行栏目。

## 视觉

沿用 `assets/site-shell.css`、`site-theme.css`、`site-brand-tokens.css`、`site-i18n.css` 的颜色、字号体系、字体、公共卡片和按钮。不得另设全局 body/:root 主题、独立页头、固定后台侧栏、第二套路由。项目局部规则以 `.journal` 限定。原动画定义与时长保留在 site-router.js，不拷贝到项目模块。

页面留白由主站 section/shell 管理。项目卡片桌面两列、窄屏一列；无横向强制宽度。重点最多三条。任务每页最多六项，验收条件展开后才展示。完整更新和文档进入独立路径。

## 口吻

用“看看进展”“如何参与”“当前重点”，不用“这是我们给你生成的”“等待发布者安装”“AI 已全部做好”等聊天或后台口吻。技术文档可以使用专业名词；介绍先说明价值和范围，不堆砌功能缩写。

只展示真实项目，缺少内容时明确说明，不生成虚构贡献者、用户数、百分比、发布时间。任务完成数量不是游戏完成度。“本地待验收”“已发布”“计划”分别标明，游戏阶段与网站包版本不能混在一起。

## 可访问性与降级

语义化标题只有一个 H1，原主导航和页脚各一套。输入有标签，筛选有按下状态，分页显示范围，详情使用原生 details/summary。键盘焦点可见，减少动态效果沿用主站。

页面数据读取失败显示错误，不把失败算成零任务；无 JS 时仍有构建时的项目、资料与任务内容。完整交互需要资源加载成功。语言控件继续由主站管理；项目正文目前为中文，不假称已完成全部英文翻译。

## 后续评审问题

新访客能否先找到可体验作品？维护文档是否抢占主要空间？新增项目是否只需登记数据？内容是否存在夸大完成度？同一动作是否沿用主站组件与转场？
